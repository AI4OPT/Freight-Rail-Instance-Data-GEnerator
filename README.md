# FRIDGE: Freight Rail Instance Data GEnerator

FRIDGE is a command-line tool that builds a graph of the United States rail network from public data and generates synthetic weekly train schedules on it, and scenario variations of those schedules.

## Getting started

This project uses `uv` for dependency and environment management. Install it [here](https://docs.astral.sh/uv/).

### Clone the repository

```sh
git clone https://github.com/AI4OPT/FRIDGE.git
cd FRIDGE
```

### Install a Gurobi license

Schedule generation solves an optimization model with [Gurobi](https://www.gurobi.com/). A Gurobi license must be installed on the machine. Academic users can get a free license through [Gurobi's academic program](https://www.gurobi.com/academia/academic-program-and-licenses/). Other options are on Gurobi's [licensing page](https://www.gurobi.com/solutions/licensing/).

### Get a BigDataCloud API key

Building the rail network reverse-geocodes every rail yard with [BigDataCloud](https://www.bigdatacloud.com/reverse-geocoding/reverse-geocode-to-city-api), which needs a free API key. Copy `.env.example` to `.env` and set `BDC_KEY`.

### Run the CLI

Run the following command to see the help menu. `uv` will automatically install all necessary dependencies.

```sh
uv run fridge --help
```

### Build the rail network

All data generated by FRIDGE is based on a graph of the United States rail network, built once with:

```sh
uv run fridge build-network
```

This downloads required public data (NTAD rail yards and rail lines, and FAF6 freight flows; the FAF5 file follows on the first schedule run) into `input_data/`, looks up the elevation and city of every yard, and builds a graph representation of United States rail to `rail_network/`. `fridge schedule` also builds the network if it is missing.

## Usage

FRIDGE has two stages: schedule generation and scenario generation. A schedule represents a weekly train plan, while a scenario represents a simulated realization of a schedule with early or late departures and arrivals.

## Schedule generation

To generate a schedule, run:

```sh
uv run fridge schedule
```

The generated files are saved to `output/<timestamp>/`. The Gurobi solutions and logs of the run go to `gurobi_solutions/<timestamp>/`, with the same timestamp. Every run solves the model again, so it needs a [Gurobi license](#install-a-gurobi-license).

To view all options, run:

```sh
uv run fridge schedule --help
```

Example - running the tool with options:

```sh
uv run fridge schedule --train-seed 39
```

`--train-seed` seeds the random choices made when turning the solved model into trains: each train's running days and departure time, and which trains get circuitous return trips. Reuse it to reproduce a schedule. The model itself does not use the seed, so a schedule is reproduced only when the model solutions are the same too; a solve that stops at `solver.time_limit_s` can end at a different solution.

`fridge schedule` looks for a config file at `configs/schedule_config.yaml`.

## Scenario generation

To generate scenarios, point `fridge scenario` at the output directory of a previous schedule run:

```sh
uv run fridge scenario --schedule-dir output/<timestamp>
```

Results are saved to `<schedule-dir>/scenarios/scenario-<timestamp>/`:

- `scenario.json` maps each schedule row ID to the days it runs. Each day holds one sample per scenario, with the departure and arrival deltas in minutes (`actual - scheduled`). Days the train does not run are omitted.
- `scenario-generation-config.yaml` is the config used, including the seed.
- `scenario-generation-report.txt` summarizes the delays at the first departure and final arrival of every train run, by train category.

`fridge scenario` looks for a config file at `configs/scenario_config.yaml`.

Distributions are `normal` (`mean`, `stdev`), `asymmetric_laplace` (`location`, `scale`, `skew`), `weibull` (`shape`, `scale`, `location`), `log_normal` (`log_mean`, `log_stdev`, `location`) or a `mixture` of these, e.g. separate early and late sides (see the [scenario README](src/railgen/scenario_gen/README.md#supported-distribution-types)). They can be written inline or defined once in `distributions_pool` and referenced by name. `default_distributions` apply to every train, and `train_category_distributions_overrides` replaces individual entries per train category.

Yard groups and legs can add their own delay on top of the train distributions:

- `yard_group_dwell_distributions`: extra minutes for dwells at a yard group.
- `leg_trip_time_percent_diff_distributions`: extra run time percentage for a one-way origin to destination leg.
- `region_distributions`: dwell and run time distributions for every yard group within a radius of a coordinate or city.

Yard groups are identified by their key. `uv run fridge yard-groups` lists all yard groups.

Example scenario config:

```yaml
general_settings:
  scenario_count: 50
distributions_pool:
  congested: { distr_type: normal, mean: 20, stdev: 10 }
train_category_distributions_overrides:
  I:
    initial_departure: { distr_type: normal, mean: 0, stdev: 2 }
yard_group_dwell_distributions:
  NORRIS-1644: congested
leg_trip_time_percent_diff_distributions:
  NEW BOYLES-943:
    NORRIS-1644:
      { distr_type: asymmetric_laplace, location: 0, scale: 3, skew: 2 }
region_distributions:
  - center: { city: Chicago, state: IL }
    radius_km: 50
    dwell_time: congested
```

### Rail network and yard groups

Running `uv run fridge build-network` again asks whether to regenerate the graph. Regenerating deletes `graph.gexf` and `all_distances.json` and reuses the yard look-ups in `rail_network/yard_records.json`.

To delete the downloaded input data (`input_data/`) and the generated network files (`rail_network/`), run:

```sh
uv run fridge clean
```

Building the network after that repeats the downloads and look-ups.

To list every yard group with its city and state, run:

```sh
uv run fridge yard-groups
```

In a terminal this opens a scrollable pager with case-insensitive `/` search. The yard group column is the key used in schedules and the scenario config.

## Tweaking Generation

In addition to the CLI arguments, every generation setting can be tweaked via a config file in `configs/`.

Every setting has a default value, so a config file can contain only the keys that differ from the defaults. Example:

```yaml
train_settings:
  speed_km_h: 120
```

Point at a different file with `--config`:

```sh
uv run fridge schedule --config other-config.yaml
```

CLI flags win over the config file, which wins over the built-in defaults.

> [!NOTE]
>
> To generate a fully-populated config file with all settings at their default values, run:
>
> ```sh
> uv run fridge config default schedule
> uv run fridge config default scenario
> ```
>
> These overwrite the files in `configs/`. Pass `-o <path>` to write somewhere else.

### Editor support

FRIDGE can generate a JSON Schema for its configs, which gives code editors language server support.

Generate both schemas with:

```sh
uv run fridge config schema
```

Each generated default config file contains a `# yaml-language-server: $schema=../schema/<name>.schema.json` line at the top, which points to the matching schema when the config is in `configs/`.
